# Описание проекта

## Назначенное задание

[P09-A. FoundationDB: транзакции и отказы](https://distsys.ru/osukhoroslov/nis2/src/branch/main/project-tasks/p09-a-foundationdb-transactions.md).

Проверяемое утверждение: FoundationDB сохраняет сериализуемость и подтверждённые записи при конфликтующих транзакциях и отказе процесса, а рост конфликтности увеличивает число повторов и хвостовую задержку.

## Выбранный технический путь

Используется авторский артефакт FoundationDB и собственные нагрузка, журнал исходов и проверка корректности.

- Реальный эксперимент: официальный контейнерный выпуск `7.3.76`, запускаемый как `foundationdb/foundationdb@sha256:3d47a2e9ee389199f1d320c985bc95a3d4eb701d9b2b5c2add8a2285588fd4fe`.
- Стенд: малый локальный многопроцессный кластер из контейнеров с разными `locality-zoneid`.
- Нагрузка: клиент на Python с FoundationDB API той же версии.
- Исходный код `apple/foundationdb@ddec61a629a9` используется как зафиксированная ревизия из задания и, при необходимости, для simulation tests; полная сборка не обязательна для реального эксперимента.

Поведенческие выводы реального эксперимента будут относиться к контейнерному выпуску `7.3.76`. Сопоставимость этого выпуска с `ddec61a629a9` отдельно не утверждается.

## Что будет сделано и как это проверить

1. **Малый кластер.** Конфигурация поднимает не менее трёх `fdbserver` и показывает доступную базу через `fdbcli status`. Управляемое завершение одного процесса фиксируется в журнале событий.
2. **Нагрузка с конфликтами.** Несколько работников выполняют read-modify-write транзакции над настраиваемым горячим набором ключей. Три уровня конфликтности задаются размером набора; seed и конфигурация сохраняются.
3. **Журнал исходов.** Для каждой логической транзакции и попытки сохраняются `run_id`, `tx_id`, ключ, времена начала и конца, номер попытки, прочитанное и записанное значения, результат и код ошибки. Формат — NDJSON.
4. **Проверка сериализуемости и сохранности.** В той же транзакции записываются новый счётчик и маркер `run/<run_id>/commit/<tx_id>` со значениями `{key, old_value, new_value}`. После остановки нагрузки проверяются непрерывность переходов, итоговые счётчики и наличие маркеров всех подтверждённых `tx_id`.
5. **Эксперимент.** Для трёх уровней конфликтности сравниваются штатный режим и один отказ процесса. Сохраняются сырые журналы, сводная таблица и графики конфликтов/повторов, throughput, p95/p99 и восстановления.

## Поддерживаемые сценарии

- Низкая, средняя и высокая конфликтность без отказа.
- Те же уровни с остановкой одного активного `fdbserver` в середине измеряемого интервала.
- Неоднозначный исход коммита обрабатывается проверкой маркера с тем же `tx_id`, чтобы повтор клиента не создавал двойной учёт.

Ожидается ноль потерянных подтверждённых записей и успешная проверка истории во всех запусках. При росте конфликтности ожидаются больше повторов, ниже throughput и выше p95/p99.

## Упрощения

- Кластер локальный и малый; выводы не переносятся на производственный масштаб.
- Проверяется один отказ процесса, без сетевых разделений и отказа машины.
- Нагрузка синтетическая и закрытая, с фиксированным числом работников.
- Проверка сериализуемости относится к выбранной read-modify-write модели, а не ко всем возможным транзакциям FoundationDB.
- Для реального стенда используется готовый выпуск; сборка закреплённой ревизии остаётся запасным путём для simulation tests.
